2. CHANGES IN THIS MILESTONE
----------------------------
Defects found by the audit and fixed:
- No per-request time limit in the conversion script: a request that never
  answered stalled a run forever. Now every request has a 2-minute limit
  (CTGENWebpConvert.request_timeout = 120000 ms). A timed-out image is listed
  as failed ("The server took too long to respond.") and the run continues;
  3 consecutive request errors stop the run; a timed-out discovery request
  stops it at once.
  Files: assets/js/ctgen-webp-convert.js (+ rebuilt .min.js), includes/init.php
- A run that failed before any image was known said "stopped after 0 of 0
  images". It now says "WebP conversion could not start: <reason>".
- readme.txt overstated one point ("large media libraries do not time out").
  Rewritten to what was verified: one image per request, 2-minute limit,
  error/stop rules, one run at a time, memory note for very large images.

Test tooling (v2/, not shipped):
- v2/tests/m4-run-all.sh: runs every check below and saves the logs.
- v2/tests/m3-browser.js item 23: request timeout (one hang, all hang,
  discovery hang).
- v2/tests/m4-timing.php: time/memory of one request for large uploads.
- Fixed two bugs in my own runner during the run (lint step quoting; stray
  generated .sh file in results). Neither affected the plugin.

Backups taken before the run: DB export and uploads archive (scratchpad);
.bak copies of ctgen-webp-convert.js/.min.js, m3-browser.js, m2-verify.php.

4. DECISIONS AND LIMITATIONS
----------------------------
4.1  GIF excluded (user decision). Rows 4-5 are therefore "rejected
     clearly" / not offered, not "converted".
4.2  Full-size copies (user decision) changed the M2 rule behind row 26.
4.3  Simulated, not real: no-WebP editor (row 10), editor save failure
     (row 13), network loss / malformed JSON / expired session / request
     timeout (row 30). This server supports WebP; failures were injected.
4.4  readme.txt: the WebP sections describe only behaviour verified here.
     The older FAQ entries (multisite support, single-size regeneration,
     deletion of theme sizes) predate this feature and were not re-tested
     in this session.
4.5  Measured on this server (Lando, PHP 7.4, Imagick, 91 s / 1 GB limits):
     one request for a 6000x4000 upload took 5.2 s and ~220 MB. Hosts with
     low memory limits may fail such images; they are then listed as
     failed and the run continues (failure path verified with injected
     errors, not with a real out-of-memory).
4.6  Not tested: other browsers than Chromium 130, multisite, media
     offloaded to S3/CDN, two administrators converting at the same time
     (the converter's temp-file + atomic rename keeps each write whole, but
     concurrency itself was not exercised).
4.7  Plugin Check on the git working copy reports dev-only files (see row
     38). Release via v2/deploy/svn-release.sh, which excludes them.
